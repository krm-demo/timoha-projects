# План развития (Roadmap)

> English version: [ROADMAP.md](ROADMAP.md)

Пункты упорядочены по важности для сдачи задания. Оценки даны в двух вариантах:

- **руками:** человек пишет код сам;
- **с агентом:** код пишет ИИ-агент, а человек проверяет.

В обоих случаях Тимоха должен уметь объяснить результат, так что оставьте время, чтобы его прочитать.

## 1. Перенос фронтенда на React + TypeScript (обязательно)

API бэкенда остаётся без изменений.

```
frontend/                      (Vite: npm create vite@latest frontend -- --template react-ts)
  src/api/client.ts            обёртка над fetch: базовый URL, JSON, Bearer-токен, {error} → исключение
  src/api/types.ts             Product, Offer, Order, ListResult… (повторяют backend/internal/catalog)
  src/auth/AuthContext.tsx     пользователь + токен, вход/регистрация/выход
  src/cart/CartContext.tsx     корзина в localStorage (та же структура, что сейчас)
  src/pages/Home.tsx           GET /api/home → каждый блок загружается своим useQuery
  src/pages/Store.tsx          фильтры ↔ параметры URL, GET /api/products
  src/pages/Product.tsx        GET /api/products/:slug
  src/pages/Cart.tsx, Checkout.tsx, Order.tsx, Orders.tsx, Login.tsx, Register.tsx
  src/components/SearchBox.tsx GET /api/search с задержкой (debounce)
  src/components/ProductCard.tsx, Header.tsx, Footer.tsx
  src/styles.css               взять за основу web/styles.css (те же цвета и компоненты)
```

- **Библиотеки:** `react-router-dom` для маршрутов вида `/product/:slug` и `/store?…`, и `@tanstack/react-query` для кэширования и состояний загрузки и ошибок.
- **Защищённые страницы:** `/checkout` и `/orders` без входа перенаправляют на `/login?next=…`.
- **Деплой:** либо на Vercel с `VITE_API_BASE` = адрес API, либо собрать в `frontend/dist` и раздавать Go-сервером через `STATIC_DIR`. Второй вариант даёт один адрес и никакого CORS.
- **Старый фронтенд:** `web/` можно оставить как превью на GitHub Pages, которое работает без бэкенда, или удалить, когда React-версия заработает.
- **Тесты:** Vitest + React Testing Library для поиска, фильтров каталога и сообщений об ошибках при оплате.

Если будет делаться умный поиск (пункт 2), делайте его **сразу в React**, чтобы не писать один и тот же интерфейс дважды.

## 2. Отличительная черта: умный поиск с pills

Полное описание: **[SMART_SEARCH-ru.md](SMART_SEARCH-ru.md)** (английская версия: [SMART_SEARCH.md](SMART_SEARCH.md)). Там проблема, интерфейс, правила разбора запроса, контракт API, изменения в коде, сценарий демонстрации, метрики, альтернативы, риски и тезисы для собеседования.

Коротко: в магазинах ключей одна и та же игра продаётся десятком почти одинаковых предложений (платформа × регион × издание × продавец), и покупатели получают ключи, которые у них не активируются.

- **Запрос → pills:** при вводе `elden ps5 до 30` понятые слова превращаются в снимаемые плашки `[PlayStation ✕] [≤ €30 ✕]`.
- **Группировка:** одна карточка на игру, её варианты показаны как pills.
- **«Работает у вас»:** у каждого варианта видно, активируется ли он в стране покупателя. Подсвечивается самый дешёвый из тех, что *заработают*, а не просто самый дешёвый.

Работает детерминированно (без LLM), это около 870 строк, в основном в новых файлах, и 3 этапа, каждый из которых можно показать отдельно.

## 4. Английский + немецкий

Подход и оценки описаны в README (раздел «Planned: English + German»). Делать в React-приложении через `react-i18next`, а не в `web/`. Умный поиск и так почти бесплатно понимает несколько немецких и русских слов в запросах (`unter 30`, `до 30`).

## 5. Улучшения бэкенда (если останется время)

- **Поиск в базе данных.** Для большого каталога перенести фильтрацию в SQL, а опечатки обрабатывать через `pg_trgm` в Postgres. Дизайн умного поиска при этом не меняется.
- **Настоящая платёжная система в тестовом режиме.** Stripe PaymentIntents в тестовом режиме с подтверждением через webhook вместо `internal/payments`.
- **Склад ключей.** Таблица `keys` с заранее загруженными кодами для каждого предложения, тогда «остаток» означает число непроданных ключей. Выдавать ключи через `SELECT … FOR UPDATE SKIP LOCKED`.
- **Refresh-токены.** Короткоживущие токены доступа плюс refresh-токен на сервере. Это заодно даёт «выйти на всех устройствах».
- **Спецификация OpenAPI и Swagger UI,** чтобы проверяющие могли попробовать API прямо в браузере.
- **Наблюдаемость.** ID запросов в логах и `/metrics` для Prometheus.
- **Кабинет продавца.** Продавцы сами создают и редактируют свои предложения.
